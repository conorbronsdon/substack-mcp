# Release verification and recovery

The Publish workflow checks npm, the MCP Registry and GitHub independently. It runs only on this repository's main branch, using aligned release metadata and a full Git history. Stable releases must advance npm's latest version; prereleases require a separate policy.

Each lookup has a ten-second headers/body deadline and a two-MiB decoded-body limit. Only HTTP 404 means absent. The initial plan fails immediately on unknown state. Post-publication verification permits three read attempts, waiting one then three seconds for transient network/rate-limit/server failures or propagation. Authorization failures, malformed responses and identity mismatches fail immediately. Exhausted verification stops the workflow. No publication command is automatically retried.

For a new version, the release target is the workflow commit. For an existing npm version, recovery uses that version's full metadata `gitHead`, requires it to be an ancestor of the checkout and verifies package identity at that commit. The registry manifest comes from that original commit. An existing GitHub tag must resolve to the same commit; annotated tags are resolved with a five-tag limit. Tags are never moved.

Before each following publication step, the workflow re-reads destination state and confirms that the target did not change. A final read verifies all three destinations. GitHub release creation is independent of whether npm needed publishing. An existing draft or prerelease, inactive Registry entry, absent npm commit/integrity metadata, mismatched tag or inconsistent npm dist-tag requires manual reconciliation.

## Operator procedure

1. Inspect the failed run and public artifact metadata. Preserve the release commit and version; do not bump a version merely to repair a missing Registry or GitHub entry.
2. From a current main checkout with dependencies installed, run `node scripts/release-state.mjs plan`. This reads public metadata and local Git history and prints the planned missing destinations; it publishes nothing. Set `GH_TOKEN` through your credential mechanism if authenticated GitHub reads are needed. Do not put tokens in command arguments.
3. If a service is unavailable or publication has not propagated, wait for it to become observable and rerun the same workflow through **Actions → Publish → Run workflow**, selecting main. The verified existing npm version is skipped; missing Registry/GitHub entries can catch up independently.
4. Run `node scripts/release-state.mjs verify` or inspect the final verification step. Successful publication commands alone do not establish success. If latest has advanced beyond the checked-out version, use the current release instead of trying to republish an older one.

If npm omitted `gitHead`, first independently establish the original release commit and exact artifact integrity (for example, by verifying available provenance and inspecting the published tarball against the release). Then manually dispatch with both `reconciled_commit` (full 40-character SHA) and `reconciled_integrity` (the exact npm sha512 integrity). Local equivalents are `RECONCILED_RELEASE_COMMIT` and `RECONCILED_NPM_INTEGRITY`. These inputs are an explicit operator attestation, not an automatic provenance check. They work only for an existing npm version without a valid gitHead; the integrity must match, the commit must be in checkout history with matching package/manifest identity, and any existing tag must agree. They cannot replace valid npm commit metadata or move tags. Never supply today's HEAD merely because it is available.

During a run, `RELEASE_TARGET` binds subsequent checks to the first verified commit. `RELEASE_MANIFEST` is the explicit temporary output path for the recovered manifest, and `GITHUB_OUTPUT` receives validated version/SHA/boolean values for workflow gates. Leave these unset for a read-only local plan.

Historical npm `gitHead` is recorded metadata, not proof that every tarball byte matches the source. The checker confirms identity, integrity-field presence and commit ancestry; it does not independently attest or rebuild historical tarballs. Missing commit metadata must be investigated and explicitly reconciled as above, never replaced silently with today's HEAD. Existing matching metadata also does not establish broader client compatibility or a successful creator workflow.
